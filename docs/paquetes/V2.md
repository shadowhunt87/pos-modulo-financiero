# V2 — Plantilla de módulo vertical

**Carril:** V · **Nivel:** N2 · **Tamaño:** M · **Ola:** 1 · **Rama:** `wp/V2-plantilla` · **Asignado (provisional):** IA-E
**Espera a:** **V0 aprobado** (`docs/CONTRATO-VERTICALES.md`). Si V0 exige enganches de V1 (origen genérico, exportar un servicio), tu plantilla usa lo que V1 deje; hasta entonces, escríbela con lo que ya existe y marca lo pendiente.
**Ficha del 2026-10-12** · documento nuevo (PAQUETES §5, carril V).

## 2. Objetivo
Una carpeta **ejemplo** completa (controller, service, DTOs, prueba e2e, entrada de menú y ayuda) que la IA del socio **copia** para empezar una vertical sin romper las convenciones ni las reglas contables. Es el «hola mundo» de una vertical: crea un documento propio y genera su asiento con `PostingService`. Toca R1, R2, R3, R5, R6.

## 3. Lee antes
- Base: `CLAUDE.md`; `AGENTS.md` (si existe); `docs/PAQUETES-DE-TRABAJO.md` §1 y §4; `docs/GUIA-PRODUCTO.md` §6; `docs/GUIA-CONTABLE-FISCAL.md` R1–R6 y §8.
- **`docs/CONTRATO-VERTICALES.md`** (manda sobre esta ficha), `docs/PLAN-v0.2.md` §2 (convenciones del socio, backend y frontend).
- Código a imitar: `src/feedback/*` (módulo pequeño completo), `src/budgets/*` (documento con estados), `src/invoicing/invoicing.service.ts` (cómo se llama a `PostingService.post` dentro de una transacción y se escribe `writeAudit`), `test/feedback.e2e-spec.ts` (esqueleto de e2e con dos empresas), `frontend/src/app/features/feedback/*` y `features/catalog/partners.ts` (pantalla de referencia), `layout/nav.ts`, `frontend/public/manual/ayuda.json`, `frontend/scripts/verificar-ayuda.mjs`.

## 4. Alcance (verificado; la ubicación final la fija V0)
- **Backend (propuesta):** `src/verticals/_template/` con `template.module.ts`, `template.controller.ts`, `template.service.ts`, `dto/`, y un README corto («copia esta carpeta y cambia el nombre»); `test/vertical-template.e2e-spec.ts`. Debe **compilar** con `npm run build` pero **no** estar registrado en `app.module.ts` de producción (si la prueba necesita registrarlo, arma un módulo de prueba aparte).
- **Frontend (propuesta):** `frontend/src/app/features/_vertical-template/` con su `*.routes.ts`, una pantalla de lista y una de formulario que cumplan la lista de GUIA-PRODUCTO §6, y entradas de ejemplo para `nav.ts`/`ayuda.json` **comentadas o en el README** (no activas). Si el verificador de ayuda exige mapear sus rutas, mapéalas en `ayuda.json` (cambio mínimo en este **archivo caliente**).
- **Manual del que copia:** `docs/plantilla-vertical.md` (pasos: copiar, renombrar, registrar el módulo, agregar permisos, menú y ayuda).
- No toques `posting.service.ts` ni `invoicing.service.ts`.

## 5. No hagas
- No registres la plantilla en producción (nadie debe ver su menú ni sus rutas).
- No pongas valores fiscales, claves ni datos reales. No agregues librerías.
- No saltes ninguna regla: esta plantilla es el modelo que copiarán; si hace trampa, todas las verticales harán trampa.
- No modifiques tablas del núcleo.

## 6. Pasos sugeridos
1. Lee el contrato y decide con V0 dónde vive la plantilla; anota la decisión.
2. Backend: documento propio con `companyId` solo del token, validación con `class-validator`, `@Roles` explícito en cada escritura, 404 para lo ajeno, `writeAudit` en la misma transacción, número correlativo dentro de la transacción.
3. Genera el asiento con `PostingService.post` (diario correcto, cuentas de `AccountingSettings`, `sourceType` según V0, `sourceId` = id del documento).
4. e2e: crear, cuadre del asiento, período cerrado, aislamiento entre empresas, roles (VIEWER recibe 403 al escribir), `AuditLog`.
5. Frontend: lista con estado vacío que enseña, formulario con `app-field-help` y `app-error-notice`, botón principal único, migas y «?».
6. Escribe `docs/plantilla-vertical.md` y prueba **tú mismo** copiando la carpeta con otro nombre y viendo que compila.

## 7. Criterios de aceptación
- `npm run build`, `npm test` y `npm run test:e2e` en verde con la plantilla incluida.
- El e2e de la plantilla demuestra: asiento que cuadra (débitos = créditos), período cerrado ⇒ 422, empresa B ⇒ 404, VIEWER ⇒ 403 al escribir, y registro en la bitácora.
- `security.e2e-spec.ts` en verde (ninguna ruta de escritura sin `@Roles`).
- Copiar la carpeta con otro nombre y registrar el módulo en una rama de prueba funciona siguiendo **solo** `docs/plantilla-vertical.md`.
- `ng build`, `ng test` y `node scripts/verificar-ayuda.mjs` sin errores.
- Ningún texto visible usa «Tercero» ni jerga sin explicación.

## 8. Cómo probar
```

# TU .env local (no se sube): DATABASE_URL=postgresql://postgres:<clave>@localhost:55450/fin_v2

npm run build && npm test && npm run test:e2e
cd frontend && npm ci && npx ng build && npx ng test --watch=false && node scripts/verificar-ayuda.mjs
```

PR con: **Qué hice**, **Archivos tocados** (calientes marcados), **Decisiones** (ubicación, cómo se evita registrarla), **Cómo probar** (incluye la prueba de «copiar y renombrar»), **Qué falta** (enganches pendientes de V1, pruebas de contrato V3).

## 10. Riesgos y trampas
- Si el modelo propio de la plantilla necesita una tabla, agrega migración y toca `schema.prisma` (caliente); minimiza (idealmente reutiliza lo existente o usa un modelo mínimo) y avísalo.
- `verificar-ayuda` recorre **todos** los `*.routes.ts` de `src/app`: las rutas de la plantilla cuentan aunque no estén en el menú.
- La plantilla envejece rápido si cambia el núcleo: déjale la fecha y la versión del núcleo al inicio.
- Una prueba que «registra la plantilla en AppModule» no debe filtrarse a producción.
