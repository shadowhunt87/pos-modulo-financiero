## 2. Objetivo
Un usuario puede activar la verificación en dos pasos, entrar con clave + código y usar códigos de recuperación. El ADMIN puede restablecer el 2FA de otro usuario. Las acciones delicadas de un ADMIN (crear o ascender un ADMIN, cambiar el correo de un ADMIN, restablecer claves, restablecer el 2FA) piden confirmación reforzada. Todo queda en la bitácora. Toca R3, R5, R12 y la regla de oro de datos reales (P10).

## 7. Criterios de aceptación (resumen; la lista completa es el anexo 6.1 y 6.2)
- Usuario sin 2FA entra como hoy; las pruebas del socio siguen en verde, salvo las 4 líneas indicadas.
- Con 2FA: sin código no hay token; código usado, viejo o fuera de la ventana → rechazado; el desafío no sirve como sesión ni al revés (incluidas las pruebas con `JWT_SECRET`, `"[object ArrayBuffer]"` y sin `aud`).
- **50 peticiones simultáneas con códigos malos → como mucho 5 respuestas 401 y el resto 429; los fallos sobreviven a un reinicio**; mismo resultado para login y cambio de clave.
- Códigos de recuperación de un solo uso, con su propio límite; entran aunque el TOTP esté bloqueado.
- Con solo un token de ADMIN (sin clave ni código): crear o ascender un ADMIN, cambiar el correo de un ADMIN, `reset-password` y E9 → 422. Con confirmación → funcionan, con bitácora visible en E11.
- E9: misma empresa (404 si no), no a sí mismo, 403 a otros roles; cierra sesiones, limpia contadores, abre 72 h de inscripción.
- Política (inyectada en la prueba): ADMIN sin 2FA y sin ventana → 403; con ventana → inscripción; `validate()` falla con política y sin llave.
- Sin llave o con `kid` distinto → 503 con aviso de usar un código de emergencia; nunca 500.
- `AuditLog` no se puede modificar (disparador); ninguna respuesta ni `changes` trae secretos.

```
# En TU .env local (no se sube): DATABASE_URL=postgresql://postgres:<clave>@localhost:55432/fin_s1

npm run build && npm test && npm run test:e2e
```
